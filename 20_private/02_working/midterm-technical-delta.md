## 1. 자연어 입력을 실제 영업시간 데이터로 변환

### 중간발표 이후 달라진 점

- 단순 키워드 매칭에서 벗어나 휴무 변경, 영업시간 변경, 복합 요청을 구분한다.
- “문 닫아”를 영업시간 질의로 잘못 해석하지 않도록 의도 분류를 보강했다.
- 추석과 같은 공휴일 표현을 날짜 범위로 변환하기 위해 휴일 캘린더 데이터를 연결했다.
- 하나의 문장에 여러 변경 요청이 들어오면 일부만 버리지 않고 복합 요청으로 처리하며, 해석하지 못한 항목은 설명 가능한 오류로 반환한다.

### 발표용 표현

> 사용자가 서비스 내부 용어를 배워야 하는 방식이 아니라, 실제 점주가 말하는 자연어를 날짜와 변경 작업으로 구조화하도록 개선했습니다. 특히 공휴일 표현은 캘린더 데이터와 연결해 실제 날짜 검증이 가능하도록 했습니다.

### 근거

- `a8e444a`: 휴일 캘린더 기반 공휴일·기간 해석
- `7eb5b80`: “문 닫아” 의도 분류 회귀 수정
- `b75eb08`: 복합 요청 파싱 및 실패 설명

## 2. 지도 앱별 Before/After를 반영 결과 검증 화면으로 확장

### 중간발표 이후 달라진 점

- 단일 목업이 아니라 Google·Kakao·Naver 플랫폼별 레이아웃과 정보 표현을 분리했다.
- 변경 전과 변경 후를 나란히 보여줘 사용자가 게시 전에 결과를 확인할 수 있다.
- 375px 모바일과 1280px 데스크톱 기준을 함께 검증해 화면 폭이 달라도 정보가 잘리지 않도록 했다.
- 지도 화면, 장소 정보, 영업시간, 휴무 상태 등 변경의 시각적 결과를 한 화면에서 확인한다.

### 발표용 표현

> 단순히 데이터가 바뀌었다고 알리는 것이 아니라, 실제 지도 서비스에서 어떻게 보일지를 플랫폼별 Before/After로 확인하게 했습니다. 따라서 점주는 게시 전에 결과를 시각적으로 검토할 수 있습니다.

### 근거

- `2dd5ae2`: Before/After 미리보기 레이아웃 및 반응형 스타일
- `737f5a1`: Google·Kakao·Naver 플랫폼별 변형
- [지도 미리보기 캡처](./QA/evidence/map-preview-2026-09-22/): 모바일·데스크톱 캡처 증거

### 과장하지 말아야 할 표현

실제 Google Maps, KakaoMap, Naver Map의 내부 화면을 그대로 복제했다고 말하면 안 된다. 현재 구현은 **실제 앱의 정보 구조와 시각적 패턴을 참고한 서비스 내 미리보기**이며, 외부 지도 서비스에 직접 게시하는 연동 자체와는 구분해야 한다.

## 3. AI 결과를 자동 게시하지 않고 검토 가능한 산출물로 처리

### 중간발표 이후 달라진 점

- 플랫폼별 홍보 문구를 생성한 뒤 점주가 직접 수정할 수 있는 편집 단계를 추가했다.
- 매장 정보와 리뷰에 없는 내용을 생성하지 않도록 사실성 검증 경로를 강화했다.
- 개인정보 마스킹과 콘텐츠 안전성 검사를 통과해야 최종 결과로 사용할 수 있다.
- 안전성 위반은 일반 서버 오류가 아니라 사용자가 수정할 수 있는 검증 오류로 반환한다.

### 발표용 표현

> AI가 만든 문구를 그대로 게시하는 구조가 아니라, 생성·검토·수정·안전성 검사를 분리했습니다. 따라서 자동화 속도와 점주 통제권을 함께 확보했습니다.

### 근거

- `fb1bde4`: 생성 결과 편집 및 API 계약 확장
- `6f7303f`: 수정된 초안에도 안전성 검사 적용
- `b28997c`: 안전성 위반을 명시적 검증 오류로 변환
- `f3d47e7`: 공개 매장 정보가 개인정보 마스킹으로 손상되지 않도록 회귀 수정

## 4. 생성시간 최적화는 수치와 조건을 분리해서 설명

중간발표는 **2026-08-22 오전**이고, `f49f67d`는 같은 날 **18:25**에 생성되었으므로 발표 이후 개선이다.

| 비교 | 기록된 결과 | 해석 |
|---|---:|---|
| Gemini 기본 thinking | 약 13~17초 | 발표 이후 비교 실험에서의 기준값 |
| `thinkingLevel: LOW` | 약 5~9초 | 같은 생성 목적·플랫폼 3종 기준 |
| 단순 비교 | 약 50% 단축 | 설정 변경 실험의 측정 범위 기준 |

### 발표용 표현

> 발표 이후 불필요한 추론 단계를 LOW로 제한해, 동일 조건에서 생성 시간을 약 50% 줄였습니다. 이 수치는 최신 운영 대시보드의 p95가 아니라 설정 변경 당시의 비교 측정값입니다.

PM QA에서 관찰된 최종 화면 표시 시간 약 35초는 모델 호출 시간과 화면·API·검토 단계를 포함한 end-to-end 체감값이므로, 위 5~9초와 같은 지표로 섞어 말하지 않는다.

근거: `f49f67d`, [Gemini 생성시간 측정 문서](./gemini-generation-latency.md)

## 5. 로그인과 서버 인증을 분리해 API를 보호

### 중간발표 이후 달라진 점

- 프론트엔드에 Firebase Google 로그인을 추가했다.
- 로그인 성공 후 발급된 Firebase ID 토큰을 API 요청에 포함한다.
- FastAPI가 Firebase Admin SDK로 토큰을 검증하고, 보호된 매장 변경·SEO 생성 API만 요청을 허용한다.
- 프론트엔드 CSP에 Firebase 로그인에 필요한 스크립트·연결 정책을 반영했다.

### 발표용 표현

> 로그인 UI만 붙인 것이 아니라, 브라우저에서 발급된 ID 토큰을 FastAPI가 다시 검증하는 서버 인증 경계를 추가했습니다. 따라서 프론트엔드 상태만 조작해서 보호 API를 호출할 수 없도록 했습니다.

### 근거

- `22dacf1`: Firebase Google 로그인 프론트엔드
- `1a6e604`: FastAPI Firebase ID 토큰 검증 및 보호 라우트
- `5326c1c`: Firebase 로그인 스크립트 CSP 허용

## 6. 배포 환경에서도 같은 설정을 재현

- CI/CD 단계에서 필수 배포 변수와 Firebase 설정 누락을 fail-closed 방식으로 차단한다.
- 프론트엔드 이미지 빌드 시 Firebase 공개 설정을 주입해 로컬과 배포 환경의 설정 차이를 줄였다.
- 배포 단계의 SSH 호스트 검증과 컨테이너 이미지 전달 경로를 명시했다.

발표용 표현:

> 로컬에서만 동작하는 데모가 아니라, 인증 설정을 포함한 프론트·백엔드 배포 구성을 CI/CD에서 재현할 수 있도록 정리했습니다.

근거: `1a6e604`, `7cf336b`

## 발표용 60초 구성

1. **문제**: 점주는 지도 서비스마다 다른 정보를 직접 찾아 수정해야 하고, 자연어 요청이 복잡할수록 입력 오류가 발생한다.
2. **핵심 변화**: 자연어를 날짜·영업시간 변경으로 구조화하고, 공휴일은 캘린더와 대조한다.
3. **검증 경험**: Google·Kakao·Naver 스타일의 Before/After 화면에서 게시 전 결과를 확인한다.
4. **AI 안전성**: 생성 문구는 점주가 편집할 수 있고, 사실성·개인정보·안전성 검사를 통과해야 한다.
5. **운영 기반**: Firebase 로그인과 FastAPI 토큰 검증, 재현 가능한 배포 구성을 추가했다.
6. **수치**: 발표 후 Gemini LOW 설정으로 기록된 생성 시간이 약 13~17초에서 5~9초로 감소했다.

## 발표에서 피해야 할 주장

- 실제 지도 앱에 자동으로 게시된다고 말하지 않는다. 현재 핵심은 서비스 내 Before/After 미리보기다.
- 5~9초를 모든 요청의 보장 시간이나 p95로 말하지 않는다.
- Firebase 로그인을 추가했다고 해서 사용자 권한·역할 관리까지 완성됐다고 말하지 않는다.
- 커밋 시점만으로 발표 당시의 모든 구현 상태를 단정하지 않는다. 발표 자료·데모 캡처가 없는 항목은 “저장소 기록 기준”이라고 표시한다.
