## 추가적인 운영 측정

thinking 설정 변경 전 별도 운영 측정에서는 다음 문제가 기록되어 있었다.

- 10~30명 동시 부하에서 `seo/generations` 요청이 약 10~60초까지 걸림
- 일부 요청은 3회 재시도를 모두 소진
- 당시 Gemini 호출 평균은 약 33.4초
- 기존 20초 timeout 때문에 정상 응답이 도착하기 전에 첫 시도가 종료되고 재시도되는 경우가 있었음

이에 따라 현재 설정은 다음과 같이 조정되어 있다.

```text
per-attempt timeout: 40초
최대 시도 횟수: 2회
재시도 간격: 0.5초부터 증가
```

정상 응답 시간을 늘려 불필요한 재시도를 줄이는 방향이다. 다만 모든 시도가 timeout되는 최악의 경우에는 약 80.5초까지 걸릴 수 있으므로, 이는 정상 경로의 성능 개선과 별도로 관리해야 한다.

## 구현 변경

`workspace/backend/src/mapkeeper/adapters/gemini_seo.py`의 Gemini 요청에 다음 설정을 적용했다.

```python
"thinkingConfig": {"thinkingLevel": "LOW"}
```

문구 생성은 이미 입력된 매장 정보와 리뷰를 바탕으로 Google·Naver·Kakao용 짧은 문구 3개를 만드는 작업이므로, 높은 추론 수준의 비용 대비 효과가 낮다고 판단했다.

## 데이터의 한계

현재 저장소에는 최신 운영 환경의 자동 latency telemetry나 p50/p95 대시보드가 없다. 따라서 위 수치는 다음을 구분해서 사용해야 한다.

- `13~17초 → 5~9초`: 설정 변경 당시의 실제 비교 측정값
- `약 35초`: PM의 사용자 체감 end-to-end 관찰값
- `약 33.4초`: thinking 설정 변경 전 운영 평균 관찰값
- `1초 미만`: 오프라인 결정적 Stub의 실행 시간이며 실제 Gemini와 비교하면 안 됨

## 발표 후 보강하면 좋은 검증

실제 최신 성능을 정량적으로 제시하려면 동일한 프롬프트와 동일한 리뷰 입력으로 각 설정을 여러 번 실행하고 아래 값을 기록한다.

1. 정상 생성 시간의 p50, p95
2. timeout 비율
3. 429·5xx 재시도 비율
4. 최종 실패율
5. thinking tokens와 출력 tokens
6. Google·Naver·Kakao 문구 품질 회귀 여부

최소 20회 이상 반복하고, 순차 실행과 10명 동시 실행을 분리하면 발표 이후에도 재현 가능한 비교 자료가 된다.
