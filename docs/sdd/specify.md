## 1. 제품 목표

디지털 채널 관리에 익숙하지 않은 소상공인이 음성과 간단한 인터뷰만으로 매장 정보를 수정하고 Google·Naver·Kakao용 홍보 콘텐츠를 만들 수 있게 한다.

최종 Beta는 상용 서비스 전체가 아니라, 50·60대 점주가 팀원의 도움 없이 실제 매장 관리 결과를 만들고 근거를 확인한 뒤 수정·승인할 수 있는 현장 검증 범위다. AI는 확인되지 않은 사실을 만들거나 최종 결정을 대신하지 않는다.

## 2. 사용자와 전제

- 핵심 사용자는 모바일 입력과 긴 설정 화면에 부담을 느끼는 소상공인이다.
- MVP에는 로그인 기능이 없으며 하나의 고정 `MVP_ACTOR_ID`를 사용한다.
- Google·Naver·Kakao API는 정상 동작한다고 가정하고 내부 파이프라인을 검증한다.
- 실제 외부 발행과 시뮬레이션 발행은 검증 기록에서 구분한다.

## 3. UC1: 음성으로 매장 정보 변경

### 기본 흐름

1. 사용자가 영업시간·임시 휴무·대표 메뉴·주차 정보 변경을 말하거나 텍스트로 입력한다.
2. 브라우저가 음성을 텍스트로 변환한다.
3. 서버가 고객 PII를 마스킹한다.
4. 결정적 파서와 선택적 Gemini 구조화기가 허용 필드의 변경안을 생성한다.
5. 사용자가 변경 전·후 값을 확인한다.
6. 사용자는 내용을 수정하거나 변경안 전체를 거절할 수 있다.
7. 명시적 승인 시 승인된 플랫폼에 대해서만 SyncJob과 PlatformSyncTask를 생성한다.
8. 화면은 플랫폼별 처리 상태와 실제 승인 변경값만 보여준다.

### 허용 필드

| 필드 | 값 |
|---|---|
| `businessHours` | `{open: HH:mm, close: HH:mm}` |
| `temporaryClosure` | `{startDate: YYYY-MM-DD, endDate: YYYY-MM-DD}` |
| `representativeMenuName` | 1~50자 문자열 |
| `parkingInfo` | 1~50자 문자열 |

### 인수 조건

- 원본 오디오는 API 요청에 포함하지 않는다.
- 음성 인식 실패 시 Proposal API를 호출하지 않고 텍스트 입력을 제공한다.
- 모호한 시간·잘못된 날짜·허용되지 않은 필드는 422로 거절한다.
- 변경값이 현재 StoreProfile과 같으면 `409 INVALID_STATE`로 거절한다.
- 여러 대표 메뉴를 한 변경값으로 인식한 경우 단일 값으로 확정하지 않는다.
- DRAFT만 수정·거절·승인할 수 있다.
- PATCH는 변경 목록 전체를 교체하고 같은 `field` 중복을 거절한다.
- 서버 저장값과 `currentValue`가 다르면 `409 STALE_PROPOSAL`이다.
- 거절은 승인 취소와 다르다. DRAFT를 `REJECTED`로 끝내며 외부 반영을 시작하지 않는다.
- 상대 날짜는 Asia/Seoul 현재 기준일로 계산해 실제 날짜를 제안하고, 계산할 수 없는 표현은 확정하지 않고 재확인한다.
- 기간 요청은 시작일·종료일을 모두 구조화한다. 두 번째 끝이 월이나 주를 생략해도 첫 번째 끝의 문맥으로 해석하며, 한쪽 끝을 읽지 못하면 읽은 쪽만 반영하지 않고 거절한다.
- 복합 요청은 모든 지원 항목을 변경안으로 만들고, 지원하지 못한 항목은 누락하지 않고 `unmappedRequests`로 안내한다.
- 실패 시 기계 판독 가능한 `error.failure.reason`, 원인 설명, 구체적 재시도 방법, 다시 시도할 수 있는 예시 문장, 마스킹된 원본 입력을 함께 반환한다.
- 화면은 원본 입력을 입력창에 되돌려 사장님이 처음부터 다시 말하지 않아도 되게 한다.
- 최종 결과의 반영 내역에서 Google 지도·네이버 지도·카카오맵 장소 상세 화면을 다시 그린(외부 지도 embed가 아닌) 미리보기로 플랫폼을 고르고 Before/After를 전환할 수 있다. 미리보기는 실제 승인 변경값(`currentValue`·`proposedValue`)만 쓰고, 사진·리뷰·별점·주소·좌표를 만들지 않으며, `미리보기 · 실제 지도 화면과 다를 수 있습니다`를 표시한다. `SUCCESS`가 아닌 플랫폼은 After에서도 변경 전 값과 미반영 안내를 보여준다. 플랫폼 연동은 모의 반영이므로 실제 지도 게시를 뜻하지 않는다 (FR-011).

## 4. UC2: 리뷰 기반 홍보 콘텐츠 생성

### 목적

| 목적 | 의미 | 현재 UI |
|---|---|---|
| `INTRODUCTION` | 상시 매장 소개글 | 매장 특징·대표 메뉴·추천 대상을 묻는 인터뷰 |
| `NEWS` | 신메뉴·할인·이벤트·휴무 등 소식 | 소식 주제·상세 내용·기간을 묻는 인터뷰와 달력 확인 |

### 기본 흐름

1. 홈 화면이 리뷰 요약 API에서 전체 리뷰 수·요약·키워드·대표 리뷰를 읽는다.
2. 사용자가 소개글 또는 새소식 목적을 선택한다.
3. 사용자가 빠른 시작 버튼, 음성 또는 텍스트로 인터뷰에 답한다.
4. 답변은 `briefText`로 합쳐지고 리뷰 키워드는 `seedKeywords`로 전달된다.
5. 선택한 대표 리뷰 ID는 `sourceReviewIds`로 전달된다.
6. Gemini 또는 결정적 Stub이 플랫폼별 결과를 생성한다.
7. 사용자는 세 결과를 검토하고 문구 직접 수정, 다른 말투로 재생성, 전체 거절, 전체 승인을 선택한다.
8. 문구 직접 수정은 확인 화면에서 세 플랫폼 문구와 키워드를 그 자리에서 고치고, 승인 전에 `PATCH /api/v1/seo/generations/{generationId}/drafts`로 저장하며 `revision`을 1 증가시킨다.
9. 다른 말투로 재생성(정중하게·친근하게·짧게)은 `briefText`를 그대로 두고 `toneInstruction`과 함께 같은 Generation을 재생성하며 `revision`을 1 증가시킨다.
10. 플랫폼별 결과를 개별 승인하거나 전체 승인할 수 있다. 승인된 플랫폼만 PlatformSyncTask를 생성한다.

### 인수 조건

- 생성 결과는 Google·Naver·Kakao 각각 정확히 하나다.
- 각 결과는 `draftText`, `keywords`, `contentRules`를 가진다.
- `sourceReviewIds`는 선택이며 최대 10개다.
- 참고 리뷰는 대상 StoreProfile 소유이며 마스킹 완료 데이터만 사용한다.
- `DRAFT`에서만 직접 수정·재생성·거절·승인할 수 있다.
- 승인은 저장된 문구를 게시하므로 직접 수정한 문구는 승인 전에 저장되어야 한다.
- 승인 요청 Body는 없고 `draftIds`를 사용하지 않는다.
- PM Beta에서는 `LocalSEOContent` 또는 동등한 승인 엔터티에 플랫폼별 승인 상태를 저장한다.
- `NEWS` 결과는 일반 소개글이 아니라 사용자가 제공한 소식과 기간을 중심으로 작성한다.
- 기간을 인식한 경우 달력에 미리 표시하고 사용자가 확인·수정할 수 있다.
- Google은 확인 가능한 사실 중심, Naver는 검색어의 자연스러운 포함, Kakao는 짧고 읽기 쉬운 안내를 생성 규칙으로 사용한다.
- 모든 플랫폼 결과는 입력에 없는 사실·과장·고객 PII를 포함하지 않아야 한다.
- 리뷰가 0건이면 `keywords`를 비우고 리뷰 기반 장점을 결과에 포함하지 않는다. UI에는 리뷰 없음 안내를 표시한다.
- 초기 질문은 3개 이내이며, 추가 확인은 별도 단계로 표시한다. 안내 문구와 실제 질문 수는 일치해야 한다.
- 결과 화면에서 문구·키워드를 직접 수정하고 특정 플랫폼·문장만 재생성할 수 있어야 한다.
- 플랫폼별 결과에는 적용한 정보와 보완 권장 사항을 표시한다.
- 이 규칙은 프롬프트 요청이 아니라 생성 응답 경계에서 강제한다. 고객 PII는 결정적으로 마스킹하고, 입력(`briefText`·`seedKeywords`·참고 리뷰·StoreProfile)이 뒷받침하지 않는 할인율·가격·순위·최상급 표현이 포함된 결과는 저장하지 않고 재시도 가능한 실패로 거절한다.

### 현재 구현과 원래 명세의 차이

기존 명세는 `briefText`와 `seedKeywords`를 별도 입력 컴포넌트에서 직접 편집하도록 정의했다. 현재 제품은 사용자의 부담을 줄이기 위해 인터뷰 답변과 리뷰 요약에서 이 값을 구성한다. 이 문서는 현재 UI를 정식 기준으로 채택한다.

기존 명세는 결과 수정을 "인터뷰 단계로 돌아가 재생성"으로만 정의했다. QA F-08에서 사장님이 결과 문구를 직접 고칠 수 없다는 점이 확인되었고, 승인은 저장된 문구를 게시하므로 확인 화면의 직접 편집을 정식 동작으로 채택했다. 따라서 UC2의 수정 경로는 두 가지이며 서로 대체하지 않는다.

| 수정 경로 | 사용자 동작 | API | 결과 |
|---|---|---|---|
| 직접 편집 (F-08) | 확인 화면에서 문구·키워드를 고친다 | `PATCH /seo/generations/{id}/drafts` | 고친 문구를 그대로 저장하고 `revision` +1 |
| 재생성 | 인터뷰 답변을 고치거나 말투 버튼을 누른다 | `POST /seo/generations/{id}/regenerate` | 세 결과를 새로 생성해 교체하고 `revision` +1 |

## 5. 지원 기능: 리뷰 요약

### API 결과

- `storeProfileId`
- `reviewCount`
- `summary`
- `keywords`
- `sourceReviews` 최대 10건

### 인수 조건

- 홈 리뷰 인사이트와 UC2가 같은 응답을 사용한다.
- 전체 리뷰 수와 실제 전달하는 대표 리뷰 수를 구분한다.
- 데모 DB에서는 전체 128건, 대표 리뷰 최대 10건을 반환한다.
- 리뷰가 없을 때는 인터뷰 답변만으로 생성할 수 있음을 안내한다.
- 리뷰가 0건이면 키워드·요약·대표 장점을 기본값으로 채우지 않는다.

## 5.1 공휴일·아주대학교 일정

공식 공휴일 데이터와 아주대학교 공개 일정은 별도 `CalendarEvent`로 수집·표준화·저장한다. Gemini 재학습이 아니라 요청과 관련된 일정만 검색해 문맥으로 제공한다.

- 지난 일정·취소·중복 일정은 추천에서 제외한다.
- 선택한 일정은 날짜를 다시 입력시키지 않고 점주 확인만 받는다.
- 홈 화면에서는 현재 날짜 기준 관련성이 높은 일정 1~3개를 추천하고 직접 작성 경로도 유지한다.
- 출처 URL·수집 시각·최종 검증 시각을 저장한다.
- 일정 조회 실패 시 일반 문구 작성은 계속한다.
- 비공개 개인·교직원 일정은 수집하지 않는다.

## 5.2 플랫폼별 결과와 게시 준비도

결과는 Google·Naver·Kakao 탭으로 구분한다. Google은 사실 중심, Naver는 자연스러운 지역·메뉴 검색어, Kakao는 짧고 빠른 안내를 사용한다. 검색 순위·상단 노출은 보장하지 않는다.

`게시 준비도`는 사실 일치성, 플랫폼 형식, 정보 완성도, 지역·업종 관련성, 일정 최신성, 가독성, 키워드 과다, 과장 표현, 이미지 필요 여부, 게시 기간을 점검한다.

프로필 진단은 매장명, 업종·카테고리, 주소, 전화번호, 영업시간, 특별 영업시간, 대표 메뉴·가격, 주차·포장·예약, 소개글, 이미지, 리뷰·답글, 최근 소식을 플랫폼별로 점검한다.

## 6. 공통 승인·상태·재시도

- 승인 API는 `Idempotency-Key`가 필수다.
- 같은 actor·같은 key·같은 승인 대상은 기존 SyncJob을 반환한다.
- 같은 actor·같은 key·다른 대상은 `409 IDEMPOTENCY_CONFLICT`다.
- 모든 성공 플랫폼은 보존하며 실패한 retryable 플랫폼만 재시도한다.
- retryable 오류는 `API_TIMEOUT`, `RATE_LIMITED`, `PLATFORM_SERVER_ERROR`다.
- `AUTHENTICATION_ERROR`, `PERMISSION_DENIED`, `PLATFORM_VALIDATION_ERROR`는 재시도하지 않는다.
- 플랫폼별 최대 시도 횟수는 3회다.

## 7. 비기능 요구사항

### 보안

- 고객 PII를 마스킹한 후에만 DB·로그·Gemini 경계로 전달한다.
- Secret은 환경변수 또는 보안 저장소에서 관리한다.
- 오류 응답은 내부 traceback과 외부 API 원문을 노출하지 않는다.

### 사용성

- 모바일 375px 이상에서 주요 CTA와 입력이 잘리지 않아야 한다.
- 음성 입력이 실패해도 텍스트 입력으로 같은 작업을 계속할 수 있어야 한다.
- 외부 Enum인 `DRAFT`는 사용자 화면에서 `검토 중`처럼 이해 가능한 문구로 표시한다.
- 한글 문장의 마지막 한두 글자가 고립되지 않도록 반응형 줄바꿈을 확인한다.

### 성능과 복구

- Gemini 호출 timeout 기본값은 20초다.
- 상태 Polling은 2초 간격, 최대 60초다.
- 프로세스 재시작 시 미완료 Task를 실패 상태로 복구한다.

## 8. 검증 범위와 완료 기준

내부 회귀 세트는 UC1의 절대·상대 날짜·기간·영업시간·주차·메뉴·복합·모호·미지원·네트워크 실패·부분 플랫폼 실패를 포함한다. UC2는 리뷰 0건/있음, 소개·신메뉴·공휴일 영업·임시 휴무·할인·대학 일정·잘못된 날짜·허위 혜택·플랫폼 실패를 포함한다.

현장 검증은 최소 5명의 50·60대 점주가 팀원 도움 없이 수행한다. 핵심 과업 완료율 80% 이상, 도움 없이 완료 70% 이상, 잘못된 변경·조용한 누락·허위 메뉴·혜택·장점·일정 0건을 Beta 완료 기준으로 삼는다. UC1 과업은 2분 이내, UC2 과업은 3분 이내를 목표로 한다.
